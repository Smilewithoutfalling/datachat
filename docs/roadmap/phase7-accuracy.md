## 2. E 系列：评测基础设施（不改模型行为）

### E0 留出集 H1（约 40 题）
- 组成：单表 18、多表 12、画图 5、陷阱 5（陷阱就是 E1 的题，放进同一个集）。
- 数据（2026-11-02 定）：**闸门没用过的**外部数据，按闸门的办法做中文 GBK 脏化（只改呈现，不改数值）。单表 = UCI Beijing Multi-Site Air Quality（CC BY 4.0，12 站合并 420,768 行）；多表 = Inside Airbnb（CC BY 4.0 / CC0，四表 21 万行）。UCI Bike Sharing 没用上 —— 空气质量表的时间维度和列数已经够撑 18 道单表题，再加一套只会摊薄逐题判定的精力。
- 流程照搬闸门（gate-phase35.md）：先写题 → 独立脚本在原始数据上算答案 → 冻结（questions_sha256 / answers.json）→ 才跑模型。**冻结以后不改题**；题出错就作废那一题，记进 DEVLOG，不在原题上改。
- 脚本：复用 scripts/gate 的结构，新目录 scripts/holdout/，报告 docs/eval/holdout_<时间>_<agent>.json。人工字段和闸门一样（human_correct / failure_class / reason / guessing），另加 `first_error_step`（审计待办：判定时记下第一个出错的 step 序号）。
  **前置（2026-11-02 核对）：多表 12 题没有 CLI 入口。** `--data` 只覆盖 sales 表
  （`run_eval.py:97` 的 help、`app/eval/runner.py:77-78` 只看这一张），`DATASETS` 是硬编码 dict。
  闸门能跑 Olist 8 张表是因为它绕开了 `run_eval.py`：`scripts/gate/run_gate.py:160` 把
  `q["dataset"]` 当路径直接传给 `analyze()`。所以 holdout runner 必须照这个形状写
  （约 150 行，见 `scripts/holdout/README.md`「但"换数据表"只对单表成立」），
  不要指望给 `run_eval.py` 加参数——那是新增 CLI 入口，属于产品行为，按仓库规矩要先开 issue。
- **使用纪律**：H1 只在三个时间点跑：基线、A 系列中途一次（可选）、终测。平时调参只用闸门 25、自造 130 和单测。S 那 1/3 的题，Hark 只看汇总分数和 failure_class 分布，不看题面和逐题输出。
- CI：和 gate-oracle 一样跑 oracle 自检（标准答案在脏表上可解），不调模型。

### E1 陷阱题（5 题，并入 H1）
- 错误前提（问一个数据里不存在的类别或年份）、误导性口径（「平均」到底是按订单还是按客户）、本该拒答的问题。
- 判对标准：指出前提不成立或口径有歧义，并且不编数字。`guessing=true` 一律判错。

### E2 过程验证器（离线，不调模型）
- 对模型生成的代码做 AST 分析：区分**读取的列**和**新建的列**，读取的列必须在 schema 里；`result = <字面量数字>` 这类硬编码答案单独标记。
- 用途：判定时的辅助证据，写进报告的 `process` 字段，**不参与自动判对**。先在已有的 13 份闸门报告上回放，统计它和人工判定的一致率。
- 落点：app/eval/process_check.py + 单测。

### E3 pass^k 报表
- 问题：网关在 temperature 0 时会缓存，`--repeat` 的几次结果完全一样（FROZEN.md 第 2 条）。
- 做法：第 i 次重复在 system 提示末尾加一行没有语义的 `run-id: <i>` 打破缓存，同时打乱题目顺序；报 pass@1 和 pass^k（k 次全对的题占比）。k 默认 3。
- 先用 5 道题做实测：加 run-id 之后，k 次之间的答案或 token 数确实会不同，才算独立化成功；如果不行，就改用 temperature 0.3，并在报告里写明。

### E4 LLM-judge（依赖 §1 第 4 条）
- 只判**结论文字**是否和数值一致、有没有过度推断；数值对错仍然由比较器 + 人工判。
- 上线条件：在闸门 25 题的人工标注上，judge 和人工的一致率 ≥ 90%（预登记），否则不用。
- 防偏差：答案位置随机化、长度不作为评分依据。

### A1 实测（2026-11-02，只做了测量，没做实现）

**结论：按本文件原来写的「前 N 个 + 频次」实现，救不了它该救的题；且代价被低估了。**

**① 靶心只有 3 道题、5 次失败。** 当前单轮 450 题次里 9 次失败 / 5 道题，其中与「模型看不见列形态」
有关的只有 `biz_013`（1/3）、`biz_014`（2/3）、`biz_020`（2/3）。另两道与列画像无关：
`emp_022` 3/3 是缺口 14b 的判分口径，`ord_004` 1/3 是缺口 11 的没赋 `result`。
全修好是 441→446/450，**98.0% → 99.1%**，`pass^3` 96.7% → 98.7%，翻转 4 题 → 1 题。修完仍是饱和题集。

**② 「前 N 个枚举」在真实数据上就看不见脏值。** 用 `biz` 实测：

| 列 | 前 5 个（top-5 + 频次） | 形态体检 |
|---|---|---|
| `order_items.sku` | `K-1018×50、K-1004×48、K-1033×37、K-1022×36、K-1005×35` —— **272 行小写全排在第 6 名之后** | `80 种，去空格/大写后只剩 40 种（写法不一致）` |
| `customers.customer_id` | `C0001×1、 C0002×1、…` —— 200 个值全唯一，第 2 个带空格纯属出现顺序的运气 | `200 种，18 行有首尾空格` |
| `customers.member_level` | `Basic×72…basic×19…` 能看见，但 `biz_014` 题面本来就写了「大小写混写」 | `6 种，去空格/大写后只剩 3 种` |

所以 A1 真正有用的字段是 **`nunique` 与「归一化后 nunique」的差值**、以及**首尾空格行数**，
不是枚举列表。`sku` 那栏即使只给「80 种」也有用（商品表只有 40 个 SKU，矛盾自现），但那已经不是「枚举值」了。

**③ token 代价。** schema 摘要在 system prompt 里占 16.3%（`sales`）～ 49.7%（`biz`）。原型实测：
top-5 枚举让 schema 涨到 **1.72–1.89×**（biz 1903→3298 字符），形态体检只 **1.35–1.47×**（→2562）。
折到 system prompt 是 +12%～+37% / +6%～+17%。全量 token 增幅**无法从历史数据反推**
（五个数据集的 token/schema 比 9.95–18.69 非单调，主导因素是步数），上界按 +27% 估，一套 648 题次多烧约 1.6M token。

**④ 基线代价被 §3 的回归判据漏掉了。** `app/tools/schema.py` 在 A 组（`_AFFECTS_RESULTS` 的
`app/tools/` 前缀），改它 `code_sha12` 必变；而 `GATE_KEYS` 唯一的门禁就是 `code_sha12`。
后果：`baselines.json` 的 **6 个基线（eval-v0～v5，6 个互不相同的指纹）全部认不到**，
台账里新批次基线列变 `—`，现有 91 份报告与它一律判不可比；`rendered_set_sha12` 同时变
（schema 直拼 system prompt），连「逐题渲染串相同」这条诊断线也断。
重建一个基线要 **648 题次 / 105 分钟 / 6.11M token**（v5 实测）。
§3 写的判据「自造 130 不比上一步差（同一 evalset 指纹）」在这里不成立 —— A1 不改 evalset，
只改 `code_sha12`，`eval-v1` 那批就是同一个形状（130 题、evalset 不变、判不可比、另立基线）。

**⑤ 所以顺序不改。** 本节开头那句「按 H1 基线的失败分布排序」优先于这条的具体排期：
先有 H1 的 `failure_class` 分布，才知道列画像要做哪几项（可能只需要「空格 + 大小写塌缩」两条）。
