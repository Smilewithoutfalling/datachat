## 0. 为什么先做评测，再做改进

- **闸门已经快到顶了**。react 单表门槛 14/15（只许 s02 错），多表 9/10（只许 m10 错）；workflow 多表 10/10（DEVLOG [25]/[28]）。在这 25 题上最多还能涨 2 题，而且这 25 题已经被逐题分析过，再在上面调就是对着测试集调参（DEVLOG [11]、[13]）。
- **自造的 130 题不能当准确率用**（docs/eval/FROZEN.md 五条：n=1、网关缓存、自造、比较器放宽、题面会变）。
- 所以 M20 的「具体目标」只能定在一套**新的留出集**上，而且要先测出基线再定目标。没有基线的目标就是拍脑袋。

结论：顺序是 **E（评测）→ 定目标 → A（改进）→ 留出集终测**。

## 2. E 系列：评测基础设施（不改模型行为）

### E0 留出集 H1（约 40 题）
- 组成：单表 18、多表 12、画图 5、陷阱 5（陷阱就是 E1 的题，放进同一个集）。
- 数据：**闸门没用过的**外部数据，按闸门的办法做中文 GBK 脏化（只改呈现，不改数值）。候选：UCI Beijing Multi-Site Air Quality（CC BY 4.0，单表，时间序列）、UCI Bike Sharing（CC BY 4.0）、一套多表关系数据（许可证在 E0 PR 里逐个核对，不合格的换掉）。
- 流程照搬闸门（gate-phase35.md）：先写题 → 独立脚本在原始数据上算答案 → 冻结（questions_sha256 / answers.json）→ 才跑模型。**冻结以后不改题**；题出错就作废那一题，记进 DEVLOG，不在原题上改。
- 脚本：复用 scripts/gate 的结构，新目录 scripts/holdout/，报告 docs/eval/holdout_<时间>_<agent>.json。人工字段和闸门一样（human_correct / failure_class / reason / guessing），另加 `first_error_step`（审计待办：判定时记下第一个出错的 step 序号）。
- **使用纪律**：H1 只在三个时间点跑：基线、A 系列中途一次（可选）、终测。平时调参只用闸门 25、自造 130 和单测。S 那 1/3 的题，Hark 只看汇总分数和 failure_class 分布，不看题面和逐题输出。
- CI：和 gate-oracle 一样跑 oracle 自检（标准答案在脏表上可解），不调模型。

### E1 陷阱题（5 题，并入 H1）
- 错误前提（问一个数据里不存在的类别或年份）、误导性口径（「平均」到底是按订单还是按客户）、本该拒答的问题。
- 判对标准：指出前提不成立或口径有歧义，并且不编数字。`guessing=true` 一律判错。

### E2 过程验证器（离线，不调模型）
- 对模型生成的代码做 AST 分析：区分**读取的列**和**新建的列**，读取的列必须在 schema 里；`result = <字面量数字>` 这类硬编码答案单独标记。
- 用途：判定时的辅助证据，写进报告的 `process` 字段，**不参与自动判对**。先在已有的 13 份闸门报告上回放，统计它和人工判定的一致率。
- 落点：app/eval/process_check.py + 单测。

### E3 pass^k 报表
- 问题：网关在 temperature 0 时会缓存，`--repeat` 的几次结果完全一样（FROZEN.md 第 2 条）。
- 做法：第 i 次重复在 system 提示末尾加一行没有语义的 `run-id: <i>` 打破缓存，同时打乱题目顺序；报 pass@1 和 pass^k（k 次全对的题占比）。k 默认 3。
- 先用 5 道题做实测：加 run-id 之后，k 次之间的答案或 token 数确实会不同，才算独立化成功；如果不行，就改用 temperature 0.3，并在报告里写明。

### E4 LLM-judge（依赖 §1 第 4 条）
- 只判**结论文字**是否和数值一致、有没有过度推断；数值对错仍然由比较器 + 人工判。
- 上线条件：在闸门 25 题的人工标注上，judge 和人工的一致率 ≥ 90%（预登记），否则不用。
- 防偏差：答案位置随机化、长度不作为评分依据。

### E 系列验收
- H1 冻结（题和答案的 sha256 写进 DEVLOG），oracle 自检在 CI 通过。
- 在 H1 上跑出两个 Agent 的**基线**（pass@1 + pass^3），由 S 人工判定。
- 用基线定 A 系列的目标（§4），**目标写进本文件后才开始 A**。

## 3. A 系列：改进（按 H1 基线的失败分布排序）

下面的顺序是按现有证据排的，H1 基线出来以后，按 failure_class 的分布重排一次。

| 步 | 内容 | 对应 | 什么时候做 |
|---|---|---|---|
| A1 | **列画像**：schema 摘要里加枚举值（前 N 个 + 频次）、数值范围、空值率、疑似缺失哨兵（「未登记」「-」「N/A」）、疑似合计行 | B09、B65（闸门 s02 / s04 / s12） | 先做，证据最多 |
| A2 | **结果合理性校验**：执行后做便宜的检查（结果为空、全是 NaN、占比之和远离 100%、数量级突变），不通过就让 Agent 再看一遍，最多一次 | B05 | A1 之后 |
| A3 | **枚举值召回**：问题里的词（「华东」「已取消」）和列的枚举值做模糊匹配，命中的放进提示 | plan.md 阶段 7 | 看 H1 里过滤类的错误多不多 |
| A4 | DuckDB 统一 CSV / Excel / SQL | plan.md 阶段 7、M21 | **有条件**：H1 多表题的失败里，join / 数据读取类占一半以上才做 |

| A6 | 反馈沉淀（👍👎 / 失败轨迹 → 聚类 → 人工入册） | plan.md 阶段 7 | 推迟：自用阶段反馈量太小 |
