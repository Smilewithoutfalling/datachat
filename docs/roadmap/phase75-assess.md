## 0. 第一页：评估不是评测，两者都不能替代对方

| | 评测（evaluation） | 评估（assessment） |
|---|---|---|
| 判什么 | 答得**对不对** | 这一环**有没有按契约工作** |
| 要不要 gold | 必须要（gold、judge、比较器） | 不要 |
| 速度 | 202 题约 25 分钟，在内网，人工跑 | 秒级，离线 |
| 载体 | 命令一 | ① 契约：pytest，判绝对对错，全绿即通过<br>② 差分：`assess --diff <before> <after>`，只列出变化、不判对错 |
| 能回答 | **绝对值**：现在准不准 | **差分**：同一个输入，这次改动让哪一环从 ok 变成 fail，或者从 fail 变成 ok |
| 不能回答 | 坏在哪一环 | 现在准不准 |

**写死的规则**：
1. 评估的任何数字都**不是准确率**，不得写进对外报告、README 或基线文件。准确率的唯一来源是 202 题评测。
2. 评估只判**确定性契约**。**评估里不许有模型判分，也不许有放宽规则。** 如果一条检查需要「酌情放过」，它就属于评测，不属于评估。前车之鉴：comparator 的放宽规则就是判分工具自己从 17 条长到 20 条的。
3. 评估和评测是快慢两层：日常改动先过评估，再按 §3 的回归范围表决定要不要跑评测。

**为什么要做**：截至 b1c6745，评测代码（`app/eval` + `scripts/eval`）约 1.11 万行，产品代码（`app/` 去掉 eval）约 0.99 万行，尺子已经比刀重。而且评测只能告诉我们「整体变好还是变坏」，说不出坏在哪一环。门禁本身的分辨率也不够：n=202、p≈0.95 时，95% 置信区间约 ±3pp，也就是 ±6 题；而判红线恰好是「比基线低 6 题」。

## 1. 产品形态（决策依据）

- **交付形态：单机桌面。口径库、题库这类知识资产按团队共享来设计。**
- 判断标准：未来三个月实际打开它的人数。S 预计以后会超过 10 人、跨部门，这部分**另开方案**。本阶段不做 RBAC、配额、租户隔离。
- 合规依据：单机部署对银行是合规优势。改成团队版，等于把「CSV 散落在每个人本机」变成「CSV 集中在一台服务器上」，多出一个需要治理的数据存储——功能升级了，合规反而降级。走团队版之前，必须先回答这个问题。
- 团队价值先用便宜的方式拿：口径库和题库做成可导出、可导入的文件，团队共享知识，不共享运行时（换工具不换知识）。
- 走团队版时的已知缺口（有代码证据）：同一会话里已有分析在跑时，`POST /sessions/{id}/messages` 直接返回 409（`app/server/app.py:757`），没有排队；没有 token 分发；没有操作审计日志。

| 步 | 内容 | 验收 | 依赖 |

| 3 修复回路 | 把沙箱能力对象注入 codegen 和 reviewer 两处 prompt；加一条有预算上限的 REPLAN 边（每轮最多一次）；reviewer 如果改了口径，就拒绝它的修复，转去 replan | ① reviewer 改口径能被单测抓到<br>② REPLAN 有没有用，用 `assess --diff` 证明 | 第 1 步 |

**关于「上游固定后输出可复现」**：模型节点做不到。网关即使在 temp 0 下也不确定（BACKLOG N7；canary 基线 `answer_varied=10`）。所以验收分两层：确定性部分（输入快照、拼出的 prompt）必须逐字节一致；模型的输出在回放时可以选择用录下来的响应。

评测降级放在最后，因为它是删除动作。现在就删，还不知道指纹、可比性元数据、翻转子集哪些后面离不开；而且删了也省不下多少时间——一次全量才 25 分钟，不是瓶颈。

### 2.1 Excel 验收矩阵

复用 `scripts/perturb.py` 现有的 9 个变体，生成 xlsx 版本；再补上 xlsx 独有的几项。

| 类别 | 具体项 | 说明 |
|---|---|---|
| 表头 | 两行表头；表头不在第一行（前面有标题行或空行）；真合并单元格 | 合并单元格在 CSV 里只能模拟，xlsx 里是真的：`read_excel` 会把合并区域除左上角以外的格子都读成 NaN |
| 值 | **公式没有缓存值**；日期序列号；千分位；百分号；货币符号；总计行 | 前两项是 xlsx 独有的。公式没有缓存值时（文件从没被 Excel 打开保存过），openpyxl 用 `data_only=True` 读到的是 None，整列聚合出来是 0，而且不报错。这和「SQL 能跑、数据不对」是同一类静默错误，**必须检测出来并明确提示，不能静默算成 0** |
| 结构 | 空 sheet；隐藏 sheet；重复列名；空列 | 选表逻辑容易踩坑 |
| 形态 | 单 sheet；多 sheet 选表 | 表名规则见下 |

**实现之前要先定的两件事**（写进第 2 步的实现 PR，由 S 拍板）：
- **表名和字典怎么挂**。现在的约定是「表名 = 文件名去掉扩展名」，同名的 `.dict.csv` 自动挂成字典（`service.py:73`、`eval/cases.py:360`）。我推荐：多 sheet 时表名用 `文件名.sheet名`；字典优先找 `foo.sheet名.dict.csv`，找不到再退回 `foo.dict.csv`（对所有 sheet 生效）。单 sheet 的文件行为和 CSV 一致。
- **体积上限**。现在单个文件上限 1 GB（`app/server/app.py:82`），这是按 CSV 定的。xlsx 是 zip 压缩包，解压后可能是原来的 10 倍，`read_excel` 又会把整本读进内存。我推荐 xlsx 单独设上限，用解压后的大小来判，具体数值等测完再定。

**加库按体积排序**：openpyxl → 导出 → `scipy.stats`。`sklearn`、`statsmodels` 要等评测证明「确实有 N 道题需要」才加，加之前先量清楚它们会让 PyInstaller 打出来的 sidecar 增大多少。

## 3. 回归范围表（替代「里程碑前跑一次」）

**按作用域分档，不按改了哪个文件分。**

| 作用域 | 必须跑 |
|---|---|
| 全局 prompt（planner、codegen、summarizer、reviewer 的主模板）、`app/graph.py`、`app/nodes/`、`app/agents/react_agent.py`、沙箱、记忆注入 | 评估全量 + **评测全量 202 题，不许只跑子集** |
| 只对某类题生效的规则（正则表、图表规则、拒答或澄清规则） | 评估全量 + 该类题的评测子集（按 `category` 筛） |
| 换模型或换网关 | 评测全量跑三次 |
| comparator、judge、gold、题库 | **最高优先级**：先用 `--rescore` 把历史报告全部按新尺子重打一遍，报出「换了尺子之后，历史读数变了多少」，再按 FROZEN.md 断代。这样才能区分是尺子变了还是产品变了 |
| UI、桌面壳、不碰分析链路的 server 路由 | 只跑现有闸门 |

**硬规则**：只有作用域本身就限定在某一类题的改动，才允许按 `category` 跑子集。全局改动会影响所有类别，这时用子集跑只会得出误导性的结论。

现状：命令一只能跑全量，还没有子集入口，第 4 步补上。补上之前，第二行这一档也用全量跑；补上之后，上面这条硬规则照样适用。

## 4. 各节点的评估契约（初版，全部是确定性检查）

| 节点 | 契约 |
|---|---|
| planner | **计划长度 > 3000 字 → WARN，并在 codegen 的 prompt 后追加「计划过长，直接写代码」**（P14 的计划有 5321 字）；计划里引用的列都在 schema 中 |
| codegen | 只引用存在的列；有 `result =` 赋值；import、内建函数都符合沙箱能力对象 |
| executor | result 的形态（类型、行数、列），以及 A2 可疑标记 |
| reviewer | 修复前后，代码里引用的列名集合、过滤条件集合不变；变了就拒绝这次修复，转去 replan。用正则或 AST 抽取，不追求完美，只求挡住「悄悄换掉分母」这一类改动 |
| summarizer | 结论里的数字都能在 result 里找到 |

「计划里点明了指标和过滤条件」这一条是启发式判断，中文散文容易误判，**不纳入契约**。

**grounding 从「标黄」改成「拦截」之前，先量假阳率**。`app/core/grounding.py:10` 写明，派生出来的数（差、和、比）也会被标成未核实。所以只对带单位的计数和金额做拦截，派生数仍然只提示。假阳率用 `report_adapter` 里的 `unverified` 计数来算。另外，产品侧和 `eval/consistency.py` 对「问题里出现的数字算不算证据」口径不一致，要统一成一份。

## 5. 台账

- **不合并**。LEDGER 是数据，要能机读、能自动生成；CHANGES 是人写的因果推理；BACKLOG 管排期。
- DEVLOG 以后只记「决策和理由」，「做了什么」交给 git log。因为是 squash 合并，**commit body 必须承接 PR 描述的全文**，否则不是移交，是丢失。
- 指纹不再作为测试断言，但每份报告的元数据里照样记录。否则以后没法判断两份读数能不能横向比较。这是 P2 的教训：写进文档的数字，必须有文件能复算出来。
