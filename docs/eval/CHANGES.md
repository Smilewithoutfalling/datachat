# 评测环境变更台账

> **`LEDGER.md` 记「跑了什么」，本文件记「改了什么、改动值多少」。**
> 判据一改，LEDGER 里只会多出一批不可比的新数字，看不出分数差是模型抖的还是尺子换了；
> 本文件负责把这条因果补上。两份文件都不自动生成，都是手写。

## 什么时候必须在这里加一条

改到下面任何一处，先加记录再动手，跑完补读数：

| 层 | 例子 | 指纹 |
|---|---|---|
| 题面 | `app/eval/cases*.py` 的 `turns` / `question` / `ground_truth` | `evalset_sha12` |
| 数据 / 字典 | `scripts/gen_eval_data.py`、`data/eval/*.csv` | `evalset_sha12` |
| prompt / 工具 | `app/react_agent.py`、`app/tools/**` | `code_sha12` |
| 判分 | `app/eval/comparator.py`、`negative.py`、`stats.py` | `code_sha12` |

`code_sha12` / `evalset_sha12` 任一变化，**旧读数一律不可直接比**。这不是建议，是 LEDGER 第一句。

## 格式

| 字段 | 要求 |
|---|---|
| 编号 | `C-xxx`，单调递增，不复用（否决的也占号） |
| 状态 | `已生效` / `待验证` / `已否决` / `待定` |
| 触发 | 指向证据：DEVLOG 编号 / 报告文件 / 复现命令。**不写「感觉」** |
| 改前 / 改后 | 同题集、同档位、k≥3；没测就写「未测」，不估 |
| 覆盖范围 | 会影响多少题。**别只写被修那几道** —— 字典进 prompt，动一句就是全表 |
| 未验证 | 明确列出没测的部分，防止下一个人把「验证过」读成「全量验证过」 |

两个 `flip_rate` 口径别混用：
- **翻转题占比** = 翻转题数 / 题数（易懂，但不是报告字段）
- **`flip_rate`** = `stats.py` 定义，逐题 `passes·(k−passes)/C(k,2)` 再平均（判据 `FLIP_MAX=0.4` 用的是这个）

## C-003 · 2026-11-09 · clarify 6 题与 prompt 的规格冲突：**决定不改**

- **状态**：待定（需要产品语义先定，不是技术问题）
- **触发**：[DEVLOG 139](../DEVLOG.md)。`neg_001–006` 真模型从未通过过一次
  （两次历史单跑 6/6 败 + 11-09 的 0/18）；同批 oracle 路径 6/6 全对。
  根因是 `react_agent.py` 的 system prompt 写着「口径有歧义时选一种最合理的作为 result」，
  而题集要求「必须反问且不执行代码」——同一段 prompt 里的拒答指令
  （`result = '无法回答：<原因>'`）反倒是做得到的（`neg_007–010` 4/4 全对）。
- **不做的理由**：
  1. 改 prompt 分段（「没有可执行目标」→反问 / 「目标明确只是口径有多种」→选一种算）
     会让 `code_sha12` 变，**11-09 的 585 次 off 调用 + 306 次 state/full 调用全部作废**，
     换来的只是三跑各 +6 题（87.2/86.7/86.7% → 90.3/89.7/89.7%）。
  2. 放宽判据（允许「执行了但说明所用口径」）等于把标准降级去适配实现，
     `cases_negative.py` 的注释已明确反对（「一旦写出 gold，就等于承认猜某个口径是对的」）。
  3. 更根本的是产品问题：用户问「帮我看看这批数据」时，给一张概览表和反问一句，
     **哪个才是对的？** 这 6 道题假定后者，现行 prompt 写的是前者。没定这个之前改哪边都是猜。
- **现在的处置**：这 6 题读数**不计入能力均值**，在 DEVLOG 与 LEDGER 结论里单独列出。
  等产品语义定了再回来改 C-003 的状态。
- **未验证**：无（没改东西）。

## C-006 · 2026-11-09 · 前提区（`constraints`）不过滤纯问句：**维持现状**

- **状态**：已否决（不加过滤）
- **触发**：记忆批规格 §2.2 第 83 行「建议先不过滤，用 `mul_022` 看实际影响再说」。
- **验收条件已满足**：`mul_022` 在 off / state / full 三档**全部通过且 strict match**。
- **一处必须记住的自我纠错**：我曾统计「前提区 66.7% 是问句」，**那个数字作废** ——
  我构造快照时给每轮都传了空 `code`，而 `fold()` 的真实判据是 `code.strip()`；
  code 为空 → 所有轮次都被当成「无代码轮」塞进前提区。要精确量化必须逐轮记录 code，
  报告结构里没有，改了还会动 A 组指纹，不值。
- **现在的行为**（实测 `mul_022` 的 state_block）：

  ```
  用户此前明确说过的前提（用户原话，除非本轮问题改了它，否则继续有效）：
  - 第1轮：只看 APP 渠道的订单。
  - 第2轮：顺便说一下这张表都有哪些字段？   ← 纯问句进了"前提"
  - 第3轮：再看已完成的。
  ```

  `constraints` 的机械规则是「成功但没执行代码的轮次」，文案承诺的却是「用户说过的**前提**」，
  两者不等价。但**没有任何实测证据表明这会造成答错**，而过滤需要一套可靠的「这句是不是纯提问」
  判据 —— 现在没有。规格给过的备选规则（以问号结尾且不含「只/排除/去掉/不要/重复」就不收）
  会静默丢掉 `mul_003`「S01 门店的累计销量是多少件？」这类**唯一约束在问句里**的题。
- **结论**：文案与行为的不一致留着，写在这里备查。真要修，先拿出「纯问句进了前提区导致答错」
  的实例，而不是先改规则。

## C-007 · 2026-11-09 · `ord_027` 补「不去重」的 alt —— **已否决**（原记「建议补」）

- **状态**：已否决。**补这条 alt 会摧毁这道题唯一的考点。**
- **触发**：C-001 落地后的全量重跑里，`ord_027` 由 11-09 上午的 **3/3 全对**变成 **0/3 全错**。

- **否决依据一：那 18 行重复是刻意注入的脏数据，不是数据缺陷。**
  `scripts/gen_eval_data.py:80` 原文：`# 整行重复 18 条（同一 order_id 录入两次），插在原行后面`；
  实测 `data/eval/orders.csv` **1218 行 / 1200 个唯一 order_id**，重复的 18 组是
  **整行逐字节相同**（不是同一订单的多条商品明细，`df.duplicated().sum() == 18`）。
  `drop_duplicates('order_id')` 在这张表上是唯一正确的读法。
- **否决依据二：字典已经明写这条，而且比 alt 更早。**
  `scripts/gen_eval_data.py:92` → 字典 `order_id` 行原文：「订单号，唯一标识一笔订单；
  **表中有少量整行重复的录入错误，同一订单号出现两次**」。
  接受"不去重"等于宣布这条字典说明和那 18 行设计一起作废。
- **否决依据三：四个 alt 的设计意图是「去重不参与歧义」。** 四个 golden 里三个带
  `drop_duplicates`，唯一不带的 alt[2] 改的是**另一个维度**（status 过滤）。原记录把
  「去重」当成歧义维度，是把两件事混成了一件。
- **修正原记录的两个数**（实测，`data/eval/orders.csv`）：

  | 来源 | 去重 | 过滤 status | 金额字段 | 实测值 |
  |---|---|---|---|---|
  | gold | ✓ | ✓（已完成） | pay_amount | **850,854.16** |
  | alt[0] | ✓ | ✗ | pay_amount | **1,021,460.51** ← 原记 858,290.45，写串行了 |

  | alt[2] | ✗ | ✓（已完成） | pay_amount | **858,290.45** |

- **真因见 C-008**：模型不是"选了一种合理口径"，是**压根没收到"有重复"这条信息**
  —— 字典检索命中不到它。修法是让信息进得去，不是把错误答案也算对。

## C-008 · 2026-11-09 · 字典检索的词面盲区：金额字段与脏数据警示都进不了 prompt

- **状态**：待验证（**优先级高于 C-007 原建议**，影响面是全表金额题）
- **触发**：C-007 的复查。零成本实测（`retrieve_notes`，不调模型）。
- **实测一：「总销售额是多少？」的 BM25 分数排名（`data/eval/orders.csv`）**

  ```
  问题 token: ['总', '销售额', '是', '多少', '？']

     1.128  status       <-- 唯一命中
     0.000  pay_amount   <-- 金额字段本身，0 分
     0.000  order_id     <-- 去重警示在这里，0 分
     0.000  （其余 8 个字段全 0）
  ```

  **问"总销售额"却看不到 `pay_amount` 的说明**（「实付金额，= 件数 × 单价 ×（1 − 折扣率）」），
  也看不到「表中有少量整行重复」这条警示。模型只能靠列名猜 —— 而列名猜不出有 18 行重复。

- **实测二：不是 C-001 造成的。** 旧字典（`8d2b74e`）与当前字典对这句话**都只命中 `status`**。
  早先记录里写的「旧字典 0 条」是路径错误导致的假阴性（`/tmp` 是 Git Bash 虚拟路径，
  Windows 原生 Python 看不到，`load_retriever` 返回 `None`）—— 已作废，不作为依据。
- **根因**：`app/tools/dictionary.py:44` 的 `search()` 是 BM25 词面匹配 + `s > 0` 过滤。
  问题的 token 是「总 / 销售额 / 是 / 多少 / ？」，而字典描述里写的是「实付金额」「整行重复」
  「录入错误」—— 没有任何一个 token 重叠，分数恒为 0，**在 `ranked[:k]` 之前就被阈值筛掉**。
  换 k 无效（其余条目就是 0 分）。
- **影响面（实测，别夸大）**：遍历全部 201 题（`DATASETS` 里的，扰动题绝对路径不在内），
  字典**零命中 11 题（5.5%）**，仅 1 条命中 20 题（10%）。但那 11 题里：

  | 结果 | 题 |
  |---|---|
  | 三跑全对（8） | `ts_003`、`ts_013`、`ord_028`、`ord_030`、`emp_025`、`inv_021`、`inv_025`、`neg_009` |
  | 三跑全错（2） | `mul_007`、`neg_006` |
  | 不在 off 全量（1） | `mem_004`（多轮） |

  **所以不是"字典检索普遍失效"** —— 列名（`pay_amount` / `qty` / `salary`）本身够自解释，
  8 道零命中题照样全对。真正的漏洞是**无法从列名推断的元信息**：
  `ord_027` 需要的"表里有 18 行整行重复"这种数据质量警示，光看列名永远猜不到。
- **候选修法：优先改题面，不是改字典（2026-11-09 修正）**

  先看题集自己的约定（实测，含 `turns` 全文）：

  | 口径 | orders 表 47 题 |
  |---|---|
  | 全对话明写「重复录入的只算一次 / 去重」 | **33 题（70%）** |
  | `ground_truth` 用 `drop_duplicates` 但全对话没写 | **5 题**：`ord_014`、`ord_027`、`ord_028`、`ord_029`、`ord_030` |

  canary 十条里四道 orders 题（`ord_007`/`ord_012`/`ord_013`/`ord_017`）**全部明写**。
  所以"明写去重"是这个题集的主流约定，那 5 题是**题面偏薄**，不是设计上要考"自己想到"。
  其中 4 题是 `ambiguity`（alt 宽容），只有 `ord_027` 的四个 golden 全要求去重。

  | 方案 | 改动 | 归属 | 判断 |
  |---|---|---|---|
