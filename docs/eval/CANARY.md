# canary：十条探针，探模型权重有没有换

> 生成/维护方式：清单在 `app/eval/canary.py`，跑法见下。**本文件里的数字是实测读数，
> 换题单就整段作废，别在旧数字上接着算。**

## 它回答什么，不回答什么

| 问题 | 能不能回答 |
|---|---|
| 代码没动、题没动、模型名也没动，读数变了——是不是权重换了？ | **能**。这就是它存在的唯一理由 |
| 这批改动让模型变强了没？ | 不能。十条是挑出来的稳定题，不构成能力抽样 |
| 为什么某题翻了？ | 不能。它只报警，归因要自己去看原始输出 |

背景：指纹体系里 `fingerprints.model` 记的只是名字 `Qwen3.5-397B-A17B`，网关后面换成哪个
快照，报告一个字符都不变。eval-v0 三次运行 `attempts` 从 22 涨到 37/38/37、prompt 逐字
未变，只能归到模型侧，但拿不出证据。这是台账缺口 3。

## 三条硬门槛

1. **必须单轮。** 多轮一拍上记忆模式（`off` 回灌 messages / `state` 渲染成数据块），
   翻转就分不清是权重变了还是编排变了。探针只能有一个变量。
2. **必须是标量答案。** `int` / `float` / `str` / `bool`。Series 与 DataFrame 的比对躲不开
   索引写成日期还是日期区间、行列谁先谁后、标签是周起始还是周结束——那些抖动属于判分器。
   这条是踩出来的，见下节。
3. **题面不能留解释空间。** 歧义类靠 `alt_ground_truths` 容错，判定边界本身在晃；
   `status` 三态下「金额合计」这类留白同理（缺口 6）。

守门由 `tests/test_canary.py` 做，其中 `test_canary_ground_truth_returns_a_scalar` 会真跑
十条 gold 检查返回类型。加题时漏了这一条，测试会拦。

## 跑法

```bash
python run_eval.py --canary --agent react --repeat 3
```

- `--agent react` 是当前基线用的 agent。换 agent 会让 `batch_key` 不同，读数不可比。
- `--canary` 与 `--case` 互斥，同时给直接报错退出，不猜你想跑哪批。
- 报告自动标 `canary: true` 与 `canary_sha12`，台账据此单独成表，**不进全量趋势**。

offline 自检（不调模型，只验证 gold 与判分自洽）：

```bash
python run_eval.py --canary --oracle
```

## 判读规则

前提：**`canary_sha12` 与 `code_sha12` 都必须和基线一致**，否则不是漂移，是换了卷子或换了尺子。

基线（2026-10-30 12:30，`code_sha12 = 7562832e9e11`）：

| 项 | 值 |
|---|---|
| 跑数 | 5 |
| 正确率 | 100% × 5，标准差 0.0pp |
| 逐题翻转 | 0（50 次判定全一致） |

判读：

- **3 跑全 10/10** → 没漂移。
- **某一跑掉 1 题** → 先重跑一次。基线 50 次判定零翻转，单点抖动更像偶发；
  但如果重跑仍掉同一题，按漂移处理。
- **3 跑里有 ≥2 跑掉题，或任何一跑掉 ≥2 题** → 判漂移。这时**不要**直接归因到权重，
  先逐条看原始输出（`outputs/eval_react_canary_*.json` 的 `code` / `answer` / `executed`）：
  有的翻转是「答案对但没给 `result` 赋值」，有的是「判分器不认某种写法」，这两类都不该记到权重头上。
- **漂移确认后**：在 LEDGER 里记一条，标注日期与新基线；`code_sha12` 没变就别重立基准，
  否则会把权重变化洗成代码变化。

## 第一版作废了：一次代价不小的教训

初版（2026-10-30 12:23）按「台账 `## 翻转题` 里出现过、且单轮、非歧义」挑，选出
`ord_004` / `ord_003` / `ord_013` / `inv_007` / `corr_003` / `corr_001` / `ts_007` / `inv_016` /
`inv_021` / `emp_022`。3 跑结果 100% / 80% / 80%，翻 3 题。逐条查原始输出，**没有一条是算错**：

| 题 | 表面现象 | 真实原因 |
|---|---|---|
| `inv_016` | 判错 | 数值逐项相同（1070 / 2258 / 2108…），只是索引写法不同：run1 给周起始 `02-26`、run2 给区间串 `02-26~03-03`、gold 是周结束 `2024-03-03`。判分器只认前两种 |
| `ord_004` | 判错 | 三跑答案都是 832.54（正确），run2/run3 只写 `print(...)`、没给 `result` 赋值，判分取到空值 |
| `emp_022` | 判错 | 「离职的主要原因」本来就允许答成司龄 / 部门离职率分布，run3 就那么答了 |

三条各有各的问题，共同点是**都不指向权重**。原因是我当时按「历史上翻过转」选题，却没查
它当初为什么翻——台账里明明写着「eval-v2 的 9 题翻转逐条查下来，2 题是尺子的问题」。

换成标量题后，同样 10 条跑 5 次：100% × 5，翻转 0。

两条教训：

1. **「翻过转」不是敏感度的证据，是「该查一下为什么」的信号。** 挑稳定探针要看它为什么稳，
   不是看它曾经不稳。
2. **判分器能力 ≠ 模型能力。** Series/DataFrame 的比对永远带着表示法约定，把这类题放进
   探针，等于用判分器的容错度去测模型。

作废的三份报告留在 `outputs/_superseded/`，不删，但别拿那些数字当基准。

## 已知局限

1. **只锁十条。** 权重漂移如果在别的能力面上（比如长链推理），这十条可能全过。
   它是**探针不是体检**：探针绿了只说明「这十个点没动」。
2. **依赖 `code_sha12` 不变。** 只要 A 组代码动过，就分不清读数变化来自代码还是权重。
   canary 的价值在「代码没动的那些天」，日常回归别用它。
3. **`canary_sha12` 覆盖题面与判分字段，不覆盖数据文件。** 数据换了而题没换，指纹不会变。
   数据指纹走报告里的 `data_sha256` / `datasets`。
4. **拒答题只有 2 条。** 拒答边界是最容易随权重游移的地方，两条偏少；等有更死板的拒答题
   再加。目前 `inv_021`（销售额）与 `emp_022`（离职原因）都因为允许近似回答而没进清单。
