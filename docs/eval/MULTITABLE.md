# 多表业务题（biz，20 条）

> 补的是**能力空白**，不是难度上限。现有 130 道单轮题全部是单表：`analyze()` 从阶段 3.5 起
> 就支持多表（`dfs['表名']`），但 `EvalRunner.frame()` 一直只调 `read_csv`，所以「多表 join」
> 这条能力从来没有被任何读数覆盖过。这批题第一次把它测出来。

## 一、数据集

`data/eval/biz/` 五张表，由 `scripts/gen_biz_data.py` 用固定种子生成（`--check` 可校验逐字节一致）：

| 表 | 行数 | 说明 |
|---|---|---|
| `orders` | 812（800 唯一 + 12 整行重复） | 只有编号/日期/客户/渠道/状态，**刻意不含金额** |
| `order_items` | 1373 | 一单 1~3 行，金额全在这里 |
| `products` | 42（40 SKU + 2 整行重复） | 品类、标价、成本 |
| `customers` | 200 | 城市（含空值）、会员等级 |
| `refunds` | 95（90 + 5 整行重复） | 既挂已退款订单，也挂少量已完成订单 |

`orders` 不放金额是有意的：销售额只能从明细算，不 join 就出不了答案，堵掉「猜一个总价」的路。

## 二、脏点清单（每一条都在题面或字典里点明）

| 脏点 | 形态 | 不处理的后果 |
|---|---|---|
| 订单整行重复 | 812 行 → 800 笔 | 各城市/各状态多 1~4 单，金额按比例虚高 |
| `status` 前后空格 | 9 种字面值 | `== '已完成'` 只命中 551/670 |
| `order_date` 带时间戳 | 83 行 `... 00:00:00` | `pd.to_datetime` 直接抛 ValueError |
| `unit_price` / `refund_amount` 混格式 | `¥1,234.50` / `1234.5` | 整列 object，不清洗无法求和 |
| `sku` 混小写 | 271 行 | 同一 SKU 拆成两组，Top5 排名变 |
| 商品表整行重复 | 42 → 40 SKU | join 后该 SKU 的明细双算 |
| `category` / `product_name` 尾空格 | 15% / 30% | 品类多出 `'数码 '` 一类 |
| 客户编号前导空格 | 18 行 | join 丢失客户，城市/等级对不上 |
| 城市空值 + 8 个客户不在表里 | 12 + 8 | 两处缺失，必须都归「未知」 |

## 三、口径原则

**题面写死口径，脏点只提示存在、不给代码。** 这批题要回答的是「模型能不能在真实数据上
把活干完」，不是「模型能不能猜出题人想要什么」。留白类能力（该不该问、该继承什么）由
ambiguity 那 8 条和多轮 33 条去测，两类混在一起会互相污染归因。

具体做法：每题题面里明确写出「订单表有整行重复，重复录入的订单只算一次」「只算已完成订单」
「商品表有整行重复，需按 SKU 去重」，与 `ord_` 系列老题的措辞一致。

## 四、读数（2026-10-30，react，`Qwen3.5-397B-A17B`）

| 轮次 | 正确 | 执行率 | 失败题 |
|---|---|---|---|
| run1 | 18/20 = 90.0% | 100% | `biz_013`（硬编码）、`biz_014` |
| run2 | 19/20 = 95.0% | 100% | `biz_014` |

对照：同一批模型在 130 道单轮题上是 130/130 = 100%（三跑全对）。

**执行率 100%，说明错的全是算错，不是没跑。** 这一点比正确率本身更重要——脏数据没有
把模型卡在语法错误上，而是卡在「以为洗干净了」。

## 五、三个发现

### 1. `biz_014` 是稳定缺口：客户编号前导空格

两轮都错，且输出完全相同（2607.48 vs 2537.39）。模型 strip 了 `member_level`，但没 strip
`customer_id`，18 个带前导空格的客户 join 不上，Gold 会员的样本就少了一批，均值偏高。

这不是运气问题：同一个错误在两轮里逐字复现，属于「想不到要 strip 主键」。

### 2. `biz_013` 第一轮是**假执行**：模型把答案硬编码

run1 的 `code` 是：

```python
top5 = pd.Series({'K-1011':138322.36,'K-1026':132267.72,...})
result = top5
```

**代码里没有 `dfs`，没有任何数据访问**，但 `executed=True`。模型在若干次尝试失败后，把
上一轮算出的数字直接写死，再以「执行成功」的身份交卷。run2 是正常计算（`sku.upper()` +
`groupby` + `head(5)`），所以判对是有效的。

这件事比一道题的对错严重：**只要答案硬编码对了，判分器无从分辨**。当前 `executed` 只表示
「代码跑通且拿到了 result」，不表示「用了数据」。这是一个独立的评测有效性缺口，见 LEDGER
缺口 12。

### 3. pandas 3 让 `is_object_dtype` 失效

`biz_019` run1 的代码用 `if pd.api.types.is_object_dtype(df[c]): df[c] = df[c].str.strip()`。
本机 pandas 是 **3.0.6**，字符串列的 dtype 是 `str` 而不是 `object`，`is_object_dtype` 返回
`False`，**整段 strip 一次都没执行**。结果 `status` 仍是 9 种字面值，`== '已完成'` 只命中
551 行，客单价从 2849.59 变成 2932.71。

这是环境层面的普遍陷阱，不只影响这一题：任何模型写出 `select_dtypes('object')` /
`is_object_dtype` 的清洗逻辑，在 pandas 3 下都会静默失效。判它错是对的（确实没洗干净），
但要知道失败原因是版本行为，不是模型不会 strip。

## 六、这批题的局限

1. **只有 90~95%，不足以当难度天花板。** 说明「多表 + 中等脏数据」这一层模型基本能吃下，
   稳定卡住它的只有「主键空格」这种极隐蔽的脏点。要更难的题得往别处走：
   口径冲突（两表对不上账）、需要业务推理的指标定义、超长链路（5 步以上聚合）。
2. **20 条里 11 条是标量答案。** 剩下 9 条 Series 题的 index 全是稳定字符串（品类、城市、
   SKU、渠道），这是刻意的：canary 那轮已经证明，index 用时间/区间表示法会天然翻转。
3. **两轮不足以谈翻转速。** 20 题两轮只观察到 1 次翻转（`biz_013`），样本太薄，
   任何「翻转率 x%」的结论都不成立。要谈稳定性得跑到 5 轮以上。
4. **`biz_002` 与其余题的口径相反。** 它问「有多少条整行重复」，不能加「重复只算一次」
   那句；已在代码里用 `_NOT_ABOUT_ORDERS` 显式排除，改题时别把它一起扫进去。
