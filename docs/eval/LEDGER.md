## 怎么读这张表

- **`code_sha12` 是唯一门禁**。同 `code_sha12` 的报告才能拿来比数字；不同就是换了尺子，
  差异里混着"代码变了"和"模型抖了"，分不开。
- **`legacy`（无指纹）只能看趋势不能当基线**。那是 2026-10 上旬的探索，指纹体系还没建。
- **`n < 10` 是单题调试**，不进表。
- **oracle 与 canary 各自成表**。oracle 拿标准答案冒充模型输出，只证明流水线与判分口径通，
  不代表任何能力；canary 是十道固定探针题，只用来探模型权重漂移。两者的正确率都**不**混进
  全量趋势的均值——十条敏感题的平均值跟 163 题的平均值不是一回事。
- **`flip` 只对同 `code_sha12` 的多次运行有意义**。跨批次算"翻转"等于把代码差异算进噪声。

### 踩坑：`--agent` 默认是 workflow，而 workflow 在 `off` 下根本不消费历史

2026-10-29 第一次跑 143 题基线时没写 `--agent`，跑出来多轮 13 题只有 **2/13（15.4%）**，
而同样代码下单独跑 13 题是 41%。差 26pp，不是噪声。

查下去是两件事叠在一起：

- `run_eval.py` 的 `--agent` 默认值是 `workflow`，而**所有历史基线都是 react**。
- `app/core/service.py` 里 `_run_workflow(...)` 只接收 `state_block`，**没有 `history` 参数**；
  `app/server/app.py:526` 也明写着 `history = turn_history(...) if agent == "react" else None`，
  `turn_snapshots(...)` 那条路是给 `state` 模式折叠工作状态用的。

**所以「workflow + off + 多轮」是评测器自己造出来的配置，产品里不存在**：runner 不区分 agent
一律传 `history`，workflow 收下就丢，不报错也不警告。这个组合下的读数没有任何产品含义。

对照批还留在台账里（workflow / 143 题 / off / 3 跑 = 91.1%），只用来说明两件事：

1. 单轮 130 题 workflow 和 react 差不多（workflow 127/130/126 vs react 128/130/127）——
   workflow 的流水线在单轮上不掉队。
2. **两批的 `pass^3` 都是 90.21%（129/143），但错法完全不同**：workflow 是"稳定地错 10 题、
   只翻 4 题"，react 是"稳定错 5 题、另翻 9 题"。同一个 `pass^3` 掩盖了这两种完全不同的失败形态，
   只看这一个数会得出"两个 agent 一样稳"的错误结论。

**没改 `--agent` 的默认值**（那是评测入口的行为变化，要先说清楚），只在 `baselines.json` 里
把 react 标成基线、workflow 标成对照。

### 判分器两条修复（打 eval-v2 之前）

eval-v2 的 3 跑里有 9 题翻转，逐条查下来 **2 题是尺子的问题，不是模型的**：

| 题 | 现象 | 归属 |
|---|---|---|
| `ord_022` | run3 的数值与 run1 逐个相同，只是索引写成 `2024年Q1`；`_QUARTER_RE` 是 `^(?:\d{4})?\s*Q([1-4])$`，不认中间那个「年」字 | 判分器 |
| `ord_018` | run1/run2 是同一份 groupby 结果，run2 只剩 `rate` 一列（判对），run1 多给 `orders`/`refunded` 两列（判错）；差别只在裹了几层 | 判分器 |

两处都只放宽"同一个答案的另一种写法"，数值比较一个字节没动：

- `_QUARTER_RE` 加 `年?`：`2024年Q1` / `2024 Q1` / `Q1` / `2024Q1` 等价。反例（数值不同、季度不同）仍判错。

  或没有任何数值列单调时仍判错；"整张表里某处出现期望值"不算（规则 10 的老边界仍守）。

修完用 `--rescore --write` 写回三份报告，**只有这两处变化**（run1 +1、run3 +1、run2 不变），
其余 141 题的判定逐个不变。写回时把判定和计数一起更新，另记两块元信息：
`run_code_sha12`（模型跑在哪份代码上）和 `rescored`（判分用的指纹 + 变化清单）——

### 对 `FROZEN.md` 第 2 条的实证反驳

`FROZEN.md` 写着"temperature 0 时同一网关对相同请求返回相同结果（B31），`--repeat` 的几次

15. **`code_sha12` 是「落盘那一刻」的代码，不是「跑的时候」的代码。** 2026-11-02 09:04–09:18
    跑 state 三跑，中途给 `runner.py` 加了结果归因的两个 dict 键。Python 模块启动时就已加载，
    **三跑实际执行的是旧代码**；但 `EvalReport.summary()` → `fingerprint()` →
    `code_fingerprint()` 是每轮落盘时才调用的，于是三份报告全标成了新指纹 `db1b660e8afc`。
    现场证据：三份报告的 `result_origins` 都是 `None`（新代码会填），而 `code_sha12` 是新值。
    后果不是"数字错了"，是**归类错了** —— 这批会被记到新尺子名下，与它真正可比的那批断开，
    而且以后没人能从报告本身看出矛盾。
    已处置：`eval_ledger.py` 的 `_CODE_SHA_OVERRIDE` 按实际执行值 `d617102729fa` 归档，
    理由逐条写在表里；判定零变化的依据是 diff（只加键、`score_detail` 未动）。
    **根因已修（2026-11-02）**：`fingerprint.py` 加 `snapshot_code_fingerprint()`，
    `run_eval.py` 在 `--rescore` 分支之后、第一轮之前调一次，此后同进程所有报告都用这一份；
    `EvalReport.fingerprint()` 改走 `report_code_fingerprint()`（有快照用快照，没快照现算）。
    `rescore.py` 保持实时计算——重判要的是「现在这把尺子」，不是「启动时的尺子」。
    边界两条：①快照是进程级全局，本轮改动**不影响 A 组哈希**（改的是 B 组的 `fingerprint.py` /
    `report.py` 与根目录 `run_eval.py`），已验证与 HEAD 的 `affects_results_sha256` 同为
    `ac1ebcd66c5a`，历史基线全部仍可比；②`_CODE_SHA_OVERRIDE` 表保留但封存，
    只服务修复之前的历史批次，不要再往里加条目。
    **纪律仍在，但理由变了**：跑批期间别动 A 组文件——现在报告不会撒谎了，风险变成
    「Python 只在首次 import 时读文件」，中途改动若被某个后 import 的模块读到，
    这批实跑的就是**混合版本**，而报告只会记启动那一版。

    判定等价已实证：用当前代码 `rescore()` 9 份源报告，**441 题的 `correct` / `match` /

    "重判用的尺子"语义没错，只是别把它当成 HEAD 的身份证。
    这一例**不在本轮修复范围内**：`apply_rescore` 记重判时刻的指纹是正确语义
    （它描述的是"我用哪把尺子重判的"），不是缺口 15 那个"跑的时候 vs 落盘的时候"的错位。
