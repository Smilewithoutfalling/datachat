# 三层的判据为什么这么定

> **操作口径看 `README.md`**（谁在跑什么、S 的两条命令、红了怎么看、什么时候断代）。
> 本文件只回答"为什么是这几个数"，以及被撤掉的旧设计。数字变了先改 README，再来改这里。
>
> **2026-11-18 现状**：LLM 那两层已从 CI 撤出（公网 runner 到不了内网网关），
> 改为 S 在内网手工跑。本文件讲的是判据本身，与"由谁触发"无关。

## 为什么 PR 不判准确率

8 题里翻 1 题就是 12.5pp。EV-C2 算过 MDE：双侧精确 McNemar 要 **6:0 才显著**（5:0 的
p 是 0.0625）。所以小样本上的任何准确率门槛拦住的都是噪声，不是退化。

PR 档唯一的红灯是 `oracle`：假模型的输出就是标准答案，判错只能是判分链路/执行器坏了。
2026-11-18 起 PR 不再跑 8 题真模型冒烟 —— 它不判红、每推一次花一次钱，而且名单里的
`mul_005` 在 v7 三跑里就是 0/3（永远答不对），连"能跑"这个信号都被它污染。

## 为什么是「202 题 × 1 跑」+ 绝对阈值

**为什么不跑 3 跑**：要给一次改动一个快信号。3 跑是 606 题次，
按 v7 实测 5.4 s/题 ≈ 55 分钟；1 跑 ≈ 18–23 分钟。judge 与题库冻结之后，重复跑买到的是
"抖动估计"，而抖动已经由 v7 的三跑与 11-18 的补测过了（写进基线文件与 BACKLOG N7）。

**为什么阈值是 6 题，以及为什么翻转只列不拦**

- v7 的 workflow+state 三跑是 194 / 192 / 192；2026-11-18 又补了两跑 193 / 195。
  **五跑跨 3 题**（192–195）。6 题 = 2 倍以上抖动，约 3pp。
  同题集同代码的两批实测差过 1.9pp（`single_off` 94.4% → 92.5%），1.9pp 以内当噪声。
- **翻转题（`pass3_ids` 里变错）只列不拦**：11-18 实测同一个 master 连续两跑，
  193 翻 2（判红）/ 195 翻 0（判绿），判红那跑通过数还**高于**基线。
  根因是网关 temp 0 并不确定（canary 基线 `answer_varied=10`），`pass^3` 是三次抽样，
  证不了"永远对"。硬拿它判红等于每次掷硬币。详见 `BACKLOG.md` N7。
- 阈值是**绝对题数**，不是百分比：题集变了百分比会漂，而题数是同一把尺子上的刻度。

**为什么"不可比"单独一档（退出码 2）**

`agent` / `memory_mode` / `model` / `n` / `evalset_sha12` / `judge_sha12` 任一不同，读数与基线
就不是同一件事。把它算成红，会逼着人去看一堆假回归；算成绿，则会让尺子悄悄漂走。
所以单列一档：动作是修流水线或断代，不是查产品代码。

**模型为什么必须与基线一致。** v7 的三跑是 `Qwen3.5-397B-A17B` / temp 0
（`fingerprints.model` 会记名字），跑在内网 `grg-aikits-test` 上。拿 GLM 的读数去对
Qwen 的 `pass^3` 名单，差多少都不可解释。所以 S 那两条命令用的是 `.env` 里那套
（= v7 的仪器），门禁也会在模型不同时退 2：**换模型 = 重立基线**。

`infra_error` 也归到这一档：网关熔断的题不是能力读数，算成"变错"会在网关打嗝时误报退化。

## 为什么 canary 不是回归套件

十条探针只锁"同一道题两次跑结果是否一致"，用来发现**权重与 judge** 的漂移。它不构成
能力抽样：十条全绿只说明这十个点没动。日常回归由 nightly 的 202 题负责，两者不要混用。

`canary_sha12` 不同 = 换了卷子（`incomparable`）；`judge_sha12` 不同 = 换了尺子
（`stale_baseline`，动作是重立基线）。产品代码不同**不阻断**比对 —— 2026-11-09 收窄过：
旧判据要求 `code_sha12` 全同，而它覆盖 prompt/工具/记忆编排，一周改好几次，结果哨兵
永远停在"该重立基线"，静默失效。

## 被撤掉的两档（2026-11-18）

| 旧设计 | 为什么撤 |
|---|---|
| PR/nightly 的 8 题真模型冒烟 | 不判红、要花钱；名单里的 `mul_005` 在 v7 里 0/3。PR 改为纯 oracle |
| nightly 的 25 题闸门 | 判据是人工填的 `human_correct`，CI 填不了，只能查结构 —— 那件事由 oracle 覆盖。闸门移到 release 档，需要时手动跑 |

release / inject / rerun 保留为手动工具：归档、录注入基线、对历史报告定向复跑。
它们不在日常三层里，也不产生日常成本。

## 仓库要配的东西

> 2026-11-18 起 LLM 那两层不再由 CI 自动触发，所以下面这些**只影响手动 dispatch**
> 与 S 在本机跑的两条命令（本机读的是 `.env`，不读仓库变量）。

| 类型 | 名字 | 用途 | 缺了会怎样 |
|---|---|---|---|
| Secret | `DATACHAT_LLM_KEY` | 真模型 | PR 档不用（本来就不调）；nightly / canary / release **报错退出** |
| Variable | `DATACHAT_LLM_BASE_URL` | 网关 | 走代码里的默认值 |
| Variable | `DATACHAT_LLM_MODEL` | 模型名 | 走代码里的默认值 |
| Variable | `DATACHAT_CANARY_ENABLED=1` | canary job 的总开关 | 手动 dispatch 不受影响，其余情况跳过 |
| Environment | `release` + Required reviewers | 人工确认 | release 档自动开跑，没有把关 |
| 权限 | Actions 允许 `issues: write` | nightly 失败开 issue | 开 issue 那步失败（job 本身已经红了） |
