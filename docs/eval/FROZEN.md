# 评测数字的使用约束

**docs/eval/ 下所有基线数字（含 DEVLOG 里的 92.3%、96.9%、98.5% 等）都不得单独引用为"准确率"。**

原因：
1. **样本量**：只有 `eval-v2`（143 题 × 3 跑）有重复测量；其余配置都是单跑。单跑的百分比不带区间，
   0.5pp 的差别说明不了任何事。
2. **网关缓存（已实测削弱，但没到可以忽略）**：B31 记录过 temperature 0 时同一网关对相同请求
   返回相同结果。eval-v1 / eval-v2 的实测反过来了——130 题里 `(tokens, code)` 三次逐字相同的
   只有 15 题（11.5%），其余每次都不同。结论：**当前网关 + 当前模型下 `--repeat` 测的是真方差**。
   但这条只查过一个网关、一个模型、两天时间，换网关或换模型后要重新验，不能默认继承。
3. **自造数据**：143 题的数据、题面、标准答案、比较器全部由本项目产出（M01），只证明流水线自洽，不证明真实数据上有效。
4. **比较器放宽**：比较器有 20 条放宽规则；按判对层级统计，约三分之一的判对不是 strict（docs/roadmap/review-M-series-response.md 附表）。
5. **题面会变**：B47、B52 等改过题面；只有报告里 `evalset.sha256` 相同的两份报告才能直接比较。

可以怎么用：同一 evalset 指纹、同一模型与网关下的**回归对比**（改了 prompt / 代码后有没有变差）。

外部有效性看阶段 3.5 闸门（docs/eval/gate_*.json，人工判定）。

## 方差地板与 allowed_fail 纪律（EV-C1）

**单跑没有 flip_rate。** 只有 `--repeat k`（k ≥ 2）的报告才有 `stability` 块。没有它的时候，
任何"这次比上次高了 1 题"的说法都不成立 —— 那不是结论，是噪声。

**flip_rate 的口径**：`passes × (k − passes) / C(k,2)` = "同一道题任取两次运行、判定不一致的
概率"。三条不许写错：

- 不是 `min(passes, k−passes)/k`：k=3 时 p=1 与 p=2 应同为 0.67，那个式子给 0.33/0.67，且**上限只有 0.5**
  —— 0.4 的门槛几乎永不触发，等于把量程砍掉一半。
- 不是"翻转题数 / 题数"：那个数回答的是"有多少题不稳"，分母是题；flip_rate 的分母是 (题, 跑对)。
  130 题 3 跑时两者分别是 2.05% 与 3.08%，量级接近但含义不同。
- k=3 时只有 **0 / 0.67 两档**（p=1 与 p=2 同值）。这是公式的性质，不是精度不够。

**闸门侧的 flip_rate 基于比较器，不是人工。** `gate_*.json` 里第 2..k 次运行没有人签过
`human_correct`，所以 `stability.basis` 恒为 `auto_correct`。拿它当"人工判定的噪声"会低估 ——
人能认出比较器判不了的答案。`stability.unjudged` 单列"执行了但比较器认不出"的题次，
它们算进 passes 时等同答错，但**不是模型翻转**。

**两条纪律**（`verdict.allowed_fail_warnings`，只告警、不改 `regression_verdict`）：

1. `flip_rate > 0.4` 的题**不得**进 `allowed_fail`。它在翻，是"还没定性"，不是"允许失败"。
   该进稳定性专项。
2. `allowed_fail` 不超过该组题量的 20%（single 15 题 → ≤3，multi 10 题 → ≤2）。

**现状（2026-11-04，m13/m13r）：workflow/single 是 4/15 = 27%，超线，这条警告是亮的。**
不是检查写错了 —— 那份名单是 10 月定的，当时没有这条纪律。要收紧只能新增 profile，
按规矩不能改旧的（thresholds.json 的 `_note`）。
