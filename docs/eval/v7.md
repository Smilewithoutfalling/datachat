## 三件事的结论

### 1. C-022 的 +8 是不是真的

**是真的。而且同一机制在 v7 的 off/state 同批对照里开出更大的口子：多轮 10/34 → 32/34（+22 题）。**

两个数字问的不是同一件事，别混：
- **+8**（C-022 自己的读数，k=1）是 `state` 档**改前 vs 改后**：多轮 24/34 → 32/34，
  同一天还跑了 full 的改前（25/34）证明模型没变。
- **+22** 是 **`off` vs `state`**（同批、同指纹、各 3 跑）：`off` 没有快照可用，`state` 有。

C-022 之前，`workflow` 的多轮题拿不到历史，末轮只能靠猜；现在 planner 同时拿状态块
（`fold()` 出来的前提行）和最近两轮的对话快照（问 + 答案摘要 + 结果形态）。

三条证据把这个差钉成系统性而不是噪声：

1. **`off` 三跑正确数完全相同（166/166/166）**，多轮也是 10/10/9 —— 差一题，还是翻转噪声的下限。
   `off` 不是随机的差，是结构性的差：它没有可用的历史，末轮问题（「那 S02 呢」「把那张表再报一遍」）
   结构性无解。
2. **`inherit:` 断言的失败数：`off` 22/33 失败 → `state`/`full` 0/33。** 这条断言是
   `--memory off` 档唯一能暴露"末轮自己重算 / 自己编前提"的闸门，它现在的读数就是
   「off 档 2/3 的多轮题在丢前提」。`exec` 断言 `off` 0/30 失败、`state`/`full` 各 0/46 失败
   （后两档多查了记忆专项的轮次），`refusal` 三档都是 0/5 ——
   差的不是"会不会写代码"，是"记不记得上一轮定了什么口径"。
3. **`off` → `state` 的涨幅几乎全落在多轮分类里**：其他分类三跑之间最多差 1 题
   （聚合 42/42/43 与歧义 13/13/13→14/13/13 各抖 1 题），多轮一档差 22 题。

### 2. react 有没有被 C-021 拖退

**没有退步。多轮 case 级 31/31/31 → 32/32/30（v6 → v7），均值 31.0 → 31.3，差 0.3 题。**

这个对照能成立，是因为 **34 道多轮题的 prompt 逐字节没变**，而这条能直接验 —— react 的报告里
带 `fingerprints.rendered.per_case`（事前可算的 prompt 哈希）。拿 11-11 的
`eval_v6_mul_state_run1.json` 与今天的 `eval_v7_react_state_run1.json` 逐题比：
**34/34 完全一致**，`data_sha256` 也同为 `abe40a78ff53`。所以这两个读数可以相减。

**单轮全量不能这样比。** `biz_001`–`biz_020` 与 `neg_010` 共 21 道题的 prompt sha 变了
（`rendered_set_sha12` `54dbd79a809a → e9a191058e77`，新值首见于 11-13 的 `biz_local_new.json`），
来源是 11-13 那次 schema 列形态注解（B65，让缺失哨兵在 prompt 里可见），**不是这一轮的三个改动**
—— 今天的 `pr_oracle.json`（set `f1f233cc334c`）与 v7 三跑同值，把这条钉死了。

`off` / `state` 的差仍然全落在多轮，但 react 的 `off` 明显比 workflow 的 `off` 能扛：
历史在 off 档是以**对话消息**回灌的（`off_context` 的 `prompt_history=history`），
而 workflow 的 planner 在 off 档拿不到任何历史。

| react | 单轮（161） | 多轮（34） | 记忆（7） | 全量 |
|---|---|---|---|---|
| `off` | 151 / 151 / 151 | 18 / 17 / 23 | 跳过 | 169 / 168 / 174 = 87.4% |
| `state` | 150 / 148 / 151 | 32 / 32 / 30 | 7 / 7 / 7 | 189 / 187 / 188 = 93.1% |

**同一批里 workflow 反超 2.3pp，但反超的位置不在多轮。** 把 202 题按分类拆开：

| 分类 | workflow/state | react/state | 差 |
|---|---|---|---|
| 单轮 161 | 157 / 157 / 156 | 150 / 148 / 151 | **workflow +21 题次** |
| 多轮 34 | 32 / 30 / 31 | 32 / 32 / 30 | 打平（workflow −1） |
| 记忆 7 | 5 / 5 / 5 | 7 / 7 / 7 | **react +6 题次** |
| 合计 202 | 194 / 192 / 192 | 189 / 187 / 188 | workflow +14 题次 = 2.3pp |

结论分三层，别混着读：

1. **v6 时期 react 的优势（多轮）被 C-022 抹平了** —— 31.0 对 31.3，已是噪声内的平手。
2. **workflow 靠单轮反超**（+21 题次 ≈ 4.6pp）。这条不是这轮改动带来的，是 react 在单轮上
   本来就要多花一次工具循环、且更容易在"多表 join + 清洗"上抖动。
3. **react 只在 7 道记忆专项上还领先，而那 2 道的差正好是 `mem_003` 与 `mem_006`** ——
   一条是真失败（植入「净销售额 = net_amount」的口径被模型先验盖掉），一条是判定缺等价分支
   （gold 只收销售额一列）。**这个领先不能当成"react 的记忆更好"来读。**

### 3. 长会话与出境

**长会话（8 轮，`mem_006`）：三档 6 跑全错，但不是记忆丢失，是 gold 只装了一列。**
末轮问「回到最开始的那个问题……把那张表再报一遍」，第 1 轮问的是「各地区的销量明细
（每个地区一行，含件数与销售额）」。模型末轮的代码是对的（`groupby('region')['units'].sum()`），
报出件数 295/190/187/180/100（合计 952）；而 `ground_truth` 只算销售额那一列
（9480/12906/8065/11745/7090，合计 49,286）。题面要两列、gold 收一列，模型报了另一列就被判错。
这跟 P10 回放抓到的两处假失败（`mul_016` 写死名单、`mul_027` 手写筛选）是同一个形态：
**判定缺等价分支。** 归入下一轮（BACKLOG 已冻结），不在本轮改 —— 改 gold 是又一次断代。

**截断（`mem_007`，专门用来撑爆 6000 token 历史上限的题）：6 跑全对且截断确实发生了。**
`state` 三跑 `memory_trimmed=['history','planner']`，`full` 三跑 `['planner']`，
6 跑全部 `match=strict`。M9「截断之后末轮还能不能答对」从盲区变成有数据：
**截断发生了，正确性没掉。**

**植入口径（`mem_003`）：6 跑全错，这条是真失败，记忆侧要看。**
用例在 `dataset_notes` 里植入「净销售额 = net_amount 列合计（实收减退款）」，
`memory_notes` 确认该条目**确实注入了**（`sha=6179f1191e2a`）。模型的拒答理由却写
「数据中没有成本字段」—— 它宁可用通用会计口径（净销售额 = 销售额 − 成本）也不用植入的条目。
判定要求点名 `net_amount`，模型点名 `成本`。这不是判分器苛刻：这条题考的就是
「植入的口径能不能覆盖模型自己的先验」，答案是覆盖不了 —— `state` / `full` 各 3 跑全灭
（`off` 档跳过该题，没有第四份读数）。

**出境：快照通道零新增红。** `scripts/egress_audit.py` 是单轮工具（没有 `--memory`，
单轮时 history 为空），所以另写了 `scripts/egress_audit_history.py`：真正喂两轮带数值的历史
（`7` 条 / `486213.55` 元），走 `analyze(..., history=..., memory_mode="state")`，
四条断言仍然复用 `app.eval.egress`。**同题对照**（同一句问题、同一张表，只差有没有历史）：

| 数据表 | 无历史 | 带两轮历史 | 新增 |
|---|---|---|---|
| `employees.csv` | 1 红：`column_values` dept 6 个取值 > 上限 3 | **同一红**（脚本标「需要人看」） | 0 |
| `orders.csv` | 0 | 0 | 0 |

`employees` 那个红是**数据字典的枚举**（`dept` 列的全部取值），历史里根本没有部门名，
所以不是快照带出去的；两条命令都要带同一句 `-q` 才可比 —— 字典是按问题相关性检索的，
换问题就连这条红都不会出现（我先踩了一次，差点把「字典没检索到」读成「历史通道干净」）。
两表都打印了「快照出现在 prompt 里：True」，防的是"没进 prompt 所以没扫到"的假绿。

## 怎么复算

```bash
# 三档 × 3 跑（workflow 三路并发约 57 分钟；不要四路以上，见 BACKLOG N1）
python run_eval.py --agent workflow --memory off   --repeat 3 --out outputs/eval_v7_wf_off.json
python run_eval.py --agent workflow --memory state --repeat 3 --out outputs/eval_v7_wf_state.json
python run_eval.py --agent workflow --memory full  --repeat 3 --out outputs/eval_v7_wf_full.json
python run_eval.py --agent react    --memory off   --repeat 3 --out outputs/eval_v7_react_off.json
python run_eval.py --agent react    --memory state --repeat 3 --out outputs/eval_v7_react_state.json

# 补跑合并（P2）：补跑覆盖主报告同 id 记录，按合并后的 cases 重算
python eval_merge.py outputs/eval_v7_wf_state_run1.json outputs/<补跑>.json \
    --out outputs/eval_v7_wf_state_merged.json

# 台账
python eval_ledger.py
```

**已知缺口**：`--repeat` 产出的 `<tag>_summary.json` 里**没有 `agent` 也没有 `fingerprints`**
（`meta` 没带这两项），只能回 `run{k}.json` 读。已在 BACKLOG「下一轮 N4」登记，
本轮不动 `run_eval.py` —— 跑到一半换入口会让同一基线混两版 `entry_sha12`（eval-v3 踩过）。

**react 两档的第三跑是分开补的（如实记账）。** 11-17 16:49 那一批的 run1/run2 已落盘，
run3 跑到 `off` 146/195、`state` 87/202 时进程被中断。补法不是全量重跑，而是克隆一份入口
加 `--only-run 3`：`run-id: 3` 后缀与 `seed 20261112+3` 的题序仍由原逻辑算出，汇总从磁盘三份
run JSON 复原后交给**原来的 `_print_repeat`**（没有第二套算术）。克隆文件不叫 `run_eval.py`，
`entry_fingerprint()` 的 `_ENTRY_FILES` 扫不到它，所以三跑的 `entry_sha12` 一致
（`c44fcc754331`，已逐份核对 6 项门禁指纹）。复原逻辑本身先拿 workflow 的 off 三跑对过账：
`aggregate` / `stability` / `runs` 与正常路径**逐字段相同**。要完整复现也可以直接跑上面那两条
`--repeat 3` 命令，两者等价。
