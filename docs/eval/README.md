说明这套评测有缺口，不是"改动安全"。

## 数字怎么用

**`FROZEN.md` 先读。** 概括：这些百分比只能做"同一指纹下的回归对比"，不能当准确率对外说。
五条理由（n=1、网关缓存、自造数据、比较器放宽、题面会变）都在那个文件里。

## 什么算回归

**450 题**：同一 `evalset_sha12` + 同一 `code_sha12` + 同一模型，分数下降才算。
指纹不同就是不可比，不许拿两把尺子算趋势（`GATE_KEYS` 的注释写了为什么不豁免）。

**25 题闸门**：按 `m13r` profile 判，`allowed_fail` 之外不许错。答对 `allowed_fail` 里的题
记为"意外答对"，**不改门槛**（改门槛只能新增 profile）。

**canary**：`flips > 0` 或通过数下降才算。它不判对错，判的是"同一道题两次跑结果不同"。

**出境审计**：四条合同任一被违反就是红。③ 的"无法用子串法判定"走 `Audit.notes`，不是红 ——
那是"我没能判"，不是"合同被违反"。

## 当前缺口

**`eval-v0`～`eval-v5` 六个基线全部认不到。** `app/tools/schema.py` 在 A 组，
[154]（合计行）与 [156]（缺失哨兵）两次改动让 `code_sha12` 变了两次，
而 `GATE_KEYS` 明写不豁免渲染串相同的情况。后果是 450 题这套现在**只能看历史，不能判回归**。

重建一次 = 648 题次 / 约 105 分钟 / 6.11M token（`eval-v5` 实测）。重建之前，
能判回归的只有 25 题闸门和 canary —— 而这两个都已经满分，**检测能力接近零**。
